# Collaboration capacity of one replica (production build)

Measured 2026-08-31, 07:49–10:09 CDT, on `e7678827a75ab43bfc85e3a9fba5c2079b7697ef` (`origin/main` at the time), built with `NEXT_DIST_DIR=.next-soak-prod NODE_ENV=production npm run build` and served by `node dist/server.mjs` on `127.0.0.1:3297` (`NODE_ENV=production`, PGlite instead of Postgres, `RATE_LIMIT=off`, `AUTH_DEV_LOGIN=force`, `GITHUB_MOCK=1`). Machine: NVIDIA RTX Spark N1X, 20 cores at 4.0 GHz, 66 GB RAM, Windows 11, Node 24.18.0, Next.js 16.3.1 — shared with other developers' builds and suites. Driver: `npm run soak:collab` scenario 1 (`SOAK_SCENARIOS=1 SOAK_N=<N> BASE_URL=http://127.0.0.1:3297 SOAK_SERVER_PID=<pid>`): N writers on **one** document, each inserting a character every 100 ms for 60 s (600 ops nominal per writer), then a 2 s quiet window; `SOAK_TYPING_MS` at its default so the rows compare with the dev-server numbers of PR [#410](https://github.com/burkeholland/markdoc/pull/410) (the activity-watcher fix, merged as `15d1d58`).

**All CPU figures are percent of one core of this machine.** The Azure Container Apps replica has 0.5 vCPU / 1 GiB (min = max = 1 replica) and an unknown clock, so halve every headroom below. Server and client CPU are `Get-Process` `TotalProcessorTime` deltas and the working set is sampled every 2 s from a separate PowerShell process over the typing + quiescence window; the same process issues `GET /api/health` every 2 s (the probe Azure uses for liveness; its `latencyMs` field is one PGlite `select 1`, so it is an event-loop-lag proxy). Before each run the machine had to be < 40 % busy for 30 s (up to 20 min, once 26); rows that got contaminated anyway say so. Time-to-converge is the soak's "quiescent after" minus its 2 s quiet window.

Read the table with the offered-load check in mind: the soak client saturates its own event loop from N = 50 on (its bookkeeping grows with N², and `setInterval` drift cut each writer's 600 ops to 384 / 157 / 81), so **from N = 50 up the server columns are floors, not the server's limit**, and the one-way percentiles at N ≥ 100 are the client's own queueing (its event-loop lag p99 was 652 ms at N = 100 and 1 599 ms at N = 150). Two processes on **two documents** is the split the task asked for: 100 writers at 69 % of the nominal rate cost the server 58 % of a core with both clients right at the 90 % line (so still a floor, if a close one) and converged 0.1 s after the last op — **≈ 85 % of a core at the full rate, so ≈ 100 writers spread over two documents is about what one core carries (≈ 50 on the 0.5 vCPU replica)**. The same 100 writers on **one document** (a scratch copy of the soak that joins the second process to the first one's document; not committed) is the hard case, because every op fans out to 99 clients: it converged (one identical 106 617-char text in both processes, on the server and in the database) at 50 % of a core — but the two clients saturated at 39 % of the nominal rate, so at full speed the same 100 writers would need ≈ 130 % of a core (1.3 ms per op with 99 recipients, against 0.8 ms with 19 and 0.85 ms with 49). A first attempt at it under a colleague's 40-thread CPU burner (machine at 100 %, the server starved to 16 % of a core) saturated the server: quiescence timed out at 120 s with ≈ 1.2 M undelivered messages per process, all 16 in-soak and 18 of 21 external health probes exceeded 10 s, and `/api/health` stayed unanswered for the next 18 minutes after the clients disconnected (event loop busy, sockets left in `CLOSE_WAIT`) until the server was restarted. Azure's liveness probe would have restarted the replica long before: **an overloaded replica does not shed load or recover on its own** — the failure mode is a restart that drops every session, not slow typing.

**Ceiling statement.** By the task's rule (largest N with server CPU < 80 % of one core *and* health p95 < 500 ms *and* convergence < 2 s) every row above passes, so **the ceiling was not reached at 150 writers with the client saturating at N = 50** — the soak client, not the server, capped the load above N = 20, and the 100-writer rows are floors too. What the runs do pin down is the price: the server spends ≈ 0.8 ms of CPU per accepted op with 19 recipients, ≈ 0.85 ms with 49 and ≈ 1.3 ms with 99 (14.9 % at 183 ops/s; 58 % at 684 ops/s over two documents; 50 % at 388 ops/s in one), so at 10 ops/s per writer **one core of this machine carries ≈ 100 writers spread over a few documents (≈ 85 %) but only ≈ 60–80 in a single document (fan-out), and the 0.5 vCPU Azure replica about half of each: ≈ 50 and ≈ 30–40**. Real typing is far below 10 ops/s per person, so those are simultaneous keystroke rates, not seats. Memory is not the limit: 666 MB peak against 1 GiB, and it follows connection count, not ops.
