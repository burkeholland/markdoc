# Infrastructure deployment runbook: `deploy/azure.ps1 -InfraOnly`

How to change production **infrastructure** in `markdoc-rg` — alert rules, the NSG rule-write tripwire, subnets, network policies, vault or environment shape — by redeploying `infra/main.bicep` through `deploy/azure.ps1 -InfraOnly -SecretsPath <clixml>`, without touching the application image, a Container App revision or the database. The README's *Production runbook: app-only releases* covers the other production mutation; this page is the checked list for this one. It is built from the read-only what-if measurements of task #1381 (the real `-InfraOnly` parameter shape, both passes) and the row classification of task #1333. Line numbers refer to `deploy/azure.ps1`, `deploy/azure-safety.ps1` and `infra/main.bicep` at `a243aa6` (2026-09-01).

Nothing in the repository runs this automatically. The lead orders each run as its own gated task, and that task body is the ship decision.

## 1. When to run one

- Only to change infrastructure: something `infra/main.bicep` declares that is not the container image. Today the template is ahead of Azure in exactly two places: the `os-patch=failed` clause of the `markdoc-postgres-backup-failure` alert (`infra/main.bicep` l.1034, l.1048) and the not-yet-created tripwire `markdoc-postgres-nsg-rule-write` (l.1071–1093); `docs/postgres-egress.md` §10 records both as "not live yet".
- Never as part of an application release. The README's app-only runbook says: "A release never overlaps another mutation on `markdoc-rg` — no `deploy/azure.ps1` run, no NAT gateway or subnet change, no OS patch window at the same time; if one is under way, wait for it to finish before step 2 (building the image in step 1 changes nothing that runs)." The reverse holds too: no release, no OS patch window (first Sunday 04:00Z, `deploy/patch-postgres-vm.ps1`), no `-ConfigureRecovery`, no NAT-gateway deletion (`docs/postgres-egress.md` Phase 5) while this runs.
- A quiet evening, one operator, one terminal, nothing else mutating `markdoc-rg`. The script holds a current-user `Global\` mutex on the secrets store for the whole run (`deploy/azure-safety.ps1` l.626–698) and refuses a second run by the same user with `Another Markdoc production operation owns this secrets store.` (l.658); nothing stops another operator's `az` commands, so agree on the window.
- It takes ≈ 6–8 minutes and changes nothing that serves traffic (§7). The risk is entirely in the template diff you are about to apply, which is why §2 ends with a fresh what-if.

## 3. What what-if cannot tell you

- **`@secure()` parameters are not resolved.** The seven secure values (`infra/main.bicep` l.36–62) are compared as expressions, not values: the action-group row (class B) is `Modify` with `after = [parameters('alertEmailAddress')]` whatever you pass, and the VM is `NoChange` even with a fake SSH key (`after.keyData` shows the live key). No what-if — fake values or the real store — proves that the store's `AlertEmailAddress` and `VmAdminSshPublicKey` still match what is live. The proof is historical: the same DPAPI store deployed this template eleven times through 2026-08-29 (`az deployment group list`), so the human check is "the store has not been rewritten since" (row 6's `LastWriteTime`).
- **A wrong SSH key** makes the VM PUT fail with `PropertyChangeNotAllowed` (`osProfile.linuxConfiguration.ssh.publicKeys[0].keyData`, l.424, cannot change on an existing VM): a hard stop inside pass 1, deployment record `Failed`, no damage — the VM keeps running and nothing else in the graph is harmed. Fix the store or its path and rerun.
- **A wrong alert e-mail** is not an error: the action-group PUT succeeds and silently re-targets the receiver, and every backup, heartbeat and tripwire alert goes there from then on. Check afterwards (§5 item 8): `az monitor action-group show -g markdoc-rg -n markdoc-postgres-alerts --query "emailReceivers[].{name:name, status:status}" -o table` → one receiver `production-owner`, `Enabled`; then `az monitor action-group show -g markdoc-rg -n markdoc-postgres-alerts --query "emailReceivers[].emailAddress" -o tsv`, **read on your screen only**, compared with the receiver you expect. Never paste the address into a report, a board message or a commit; write "receiver unchanged".
- **Outside the picture:** the container app's live shape (`Ignore`, so what-if never compares it with the template; #1408 verified the probes equal it (§6), the rest of the app's shape is unverified — irrelevant here, relevant to any future run *with* an image); provider-side effects of a same-shape re-PUT — the vault answers the `daily-7-days` re-PUT with its built-in Sev0 "Modify policy" alert, which `markdoc-backup-policy-redeploy-suppression` strips (l.1178–1182), and a "Configure backup" job may appear in the vault's job list after pass 2 re-PUTs the protected item.

## 6. Rollback

- **Incremental mode never deletes**, so a run can only have added or re-shaped resources. After today's template the additions are exactly two, each with its own undo:
  - **Alert clause (C) → forward fix.** The `os-patch=failed` clause is the wanted state (`deploy/azure-safety.tests.ps1` l.1377 pins it: a failed guest patch must reach the backup-failure alert), so removing it is a template change like any other: edit `infra/main.bicep` l.1034/l.1048 and the pin on a branch, get it merged and accepted, run this runbook again at that SHA. Do not hand-edit the rule in the portal — the next deployment would put the template back.
  - **Tripwire (D) → by hand.** `az monitor activity-log alert update -g markdoc-rg -n markdoc-postgres-nsg-rule-write --enabled false` silences it at once; `az monitor activity-log alert delete -g markdoc-rg -n markdoc-postgres-nsg-rule-write` removes it. No redeploy removes a created resource, and the next `-InfraOnly` run re-creates it enabled (`enabled: true`, l.1076) unless the template changes too, so a permanent removal is also a template change.
- **Never redeploy `1975b96`** (the last template deployed as of 2026-09-01; record `markdoc-1975b962269b-infra`, 2026-08-29) or any other older template "to go back". An incremental deployment re-applies everything that template still declares, and the template has moved on: (1) `1975b96` declares `postgresNatGateway`, `postgresNatIp` and the `postgres` subnet's `natGateway` reference, so the run re-attaches `markdoc-pg-egress` to the subnet — or re-creates the gateway and its IP (≈ $36.53/month) once `docs/postgres-egress.md` Phase 5 has deleted them — undoing Phases 3–5; (2) it lacks the `privateEndpointNetworkPolicies: 'Disabled'` pins (l.332, l.350), so both subnets flip to the API default `Enabled` and `markdoc-pg-nsg`'s deny-all-inbound starts applying to the Azure Monitor private-endpoint NIC, breaking the private telemetry path (the hazard #1333 closed); (3) its `postgres` subnet carries only the `Microsoft.Storage` service endpoint, so the `Microsoft.KeyVault` endpoint disappears and Key Vault traffic leaves the explicit path. It would not even remove the tripwire (incremental never deletes). Rollback is always forward: change `main`, get it accepted, deploy that SHA.
- **Probes are not part of this — and they are already live.** `573ac31`'s Container App probes (`infra/main.bicep` l.1307–1323: Startup on `/api/health`, Liveness on the DB-free `/api/health?probe=live`, both `timeoutSeconds: 5`) have been in production since revision `markdoc--0000021` (2026-08-30 01:00Z), written by a CLI `az containerapp update` PATCH of the whole template rather than by `deploy/azure.ps1`; every app-only release since inherited them unchanged (task #1408 verified revisions 21–29 field by field against the template on 2026-09-01). Nothing here changes them: `-InfraOnly` sends `image=''`, so the container app is `Ignore` (l.1246), and `az containerapp update --image` keeps the revision's probes. No ARM deployment record carries them (the last deployment that wrote the container app is `markdoc-ba24a765b752-infra`, 2026-08-28), so a future full deployment *with* an image re-writes the same values — no diff, nothing to apply.

## 7. What this does not do

- **No image.** `-InfraOnly` skips the ACR build: `Resolve-ApplicationArtifact` returns `Image=''`, `AppVersion=''` (`azure.ps1` l.797–800); `az acr` is never called.
- **No Container App change, no new revision.** `containerApps/markdoc` is `if (!empty(image))` (`infra/main.bicep` l.1246) → `Ignore`. The managed environment is re-PUT with the same shape (class A: its peer-authentication and peer-encryption defaults equal live, the workspace reference resolves to the live `customerId`); an environment PUT creates no revision and restarts nothing. `/api/health` `version` stays what it was.
