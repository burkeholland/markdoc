## 2026-08-25

### Organising

- The dashboard paints in the saved sort order from the first frame (#165): the sort lived only in `localStorage`, so the server always rendered *Recently opened* with the select reading `recent`, and after hydration the client read storage, flipped the select and reordered every card — 1.6–2.3 s of the wrong order on each load in development. Changing the sort now also writes a `markdoc.dashboardSort` cookie (`SameSite=Lax`, `Path=/`, one year, `Secure` over https); `src/app/page.tsx` reads it and passes `initialSort` to `Dashboard`, so the server markup already has the saved order and the select's value and nothing moves on hydration. `localStorage` keeps being written and is the fallback for a browser that stored the sort before the cookie existed: when no cookie is set, the stored value is adopted once and the cookie written, so the next load is right from the first paint. `dashboard-org.spec` reads the navigation response's HTML (option `selected`, first card) and runs a rAF sampler from document start for 3 s asserting a single `select:cards` snapshot, plus the localStorage → cookie migration.

- Dashboard card excerpts read like the rendered text (#158, #159): the one-line excerpt under a card's title used to strip a handful of Markdown characters and let everything else through — `pixel(/api/assets/…)` for an image, `link(https://x.y)` for a link, `| a | b | | | | | 1 |` for a table. `excerpt()` now runs on the linear `excerptOf` helper next to the document stats (front matter anywhere at the top and fenced code skipped, headings passed over, images → alt text, links → text, table separator rows dropped, cells joined by spaces, emphasis / code delimiters removed, 160 chars, stops scanning once it has enough) so the cards say `Hello pixel world.` and `Para bold link a b 1 2`; the excerpt is computed from the content on every list request, so existing documents are right without a repair step. In the version history, an unnamed row no longer repeats itself (`Autosaved · v1 / Auto / v1`): the title is `Autosaved`, the kind chip appears only on named rows, and the number stays once in the meta line.
- Dashboard cards carry a storage chip only when the document is linked to GitHub — it reads **GitHub** with the repo path or gist in its tooltip — so plain documents no longer all say "Markdoc" in the grid, the list or the Trash (#114); on phone, *Show all starred* has a 44 px tap target (24 px on desktop) and the phone dashboard axe scan now enforces WCAG 2.2 `target-size` (#116).

### Writing

- The 12k-word document says "saved" ~0.9 s sooner after a warm open (#118, task #551): between `markdoc:connect` and `local-loaded` the main thread ran one ~900–1 000 ms task that applied the IndexedDB copy into Y.Text and the code pane *and* parsed the whole 86 KB with micromark — the outline asked the binding for the headings from inside the React render that the local copy triggered, and the rich pane's highlight plugin asked for the source map — so the WebSocket `open` and the server's sync queued behind it. While the initial load is coalesced, `getHeadings()` / `getSourceMap()` now answer from the last parse instead of parsing, the held text is parsed in an idle task of its own (1 s at the latest) and the rich-pane rebuild follows in another, so the local-apply task is the Yjs apply + one CodeMirror dispatch + one React render (~200–400 ms dev), the socket opens ~90 ms after `local-loaded` and `synced` → `saved` is unchanged; the server-rendered stand-in stays up until that rebuild. Measured in development on a shared box at ~85 % CPU (medians, interleaved against main): `connect → saved` 1 960 → 1 030 ms, longest main-thread task 1 020 → 800 ms (the parse alone; 560 ms when the box was calmer), `navigation → saved` 3.3–3.9 → 2.4–3.0 s. `scale.spec` test 1 lowers the `navigation → saved` budget from 3 300 to 2 800 ms and adds a longest-task assertion (1 000 ms local) from a `longtask` PerformanceObserver; the 300 ms target needs the micromark parse itself split across tasks (its streaming `write` allows it), noted as the follow-up. The `document.cookie` read in the #527 profile is Next's own inline `next-instant-navigation-testing` check — a single first-access read that pays the browser-process IPC — not app code.
- Pasting tab-separated plain text makes a table (#166): a block of `text/plain` with two or more lines and the same number of tabs on every line — what Excel, Numbers, Sheets' *Paste without formatting*, `psql` and `jq -r @tsv` put on the clipboard — used to land as one paragraph per row with invisible tabs. Both panes now insert a GFM table (first row as header, cells trimmed, `|` and Markdown syntax escaped) through the same serializer the HTML-table path uses, so the columns are padded like any other table. A single line with tabs, ragged rows and a paste inside a code block are unchanged, and a clipboard that already carries an HTML `<table>` keeps going through the HTML path. The paste is one undo step (Ctrl+Z restores the raw text) and a toast offers *Undo*. Unit tests cover the detector, both panes' handlers and the undo; `e2e/paste.spec.ts` pastes the 3×3 block into each pane and asserts the table count, the `| Name  | Qty | Price |` source and Undo.
- The server-rendered preview shown while a document opens now uses the editor's type scale, so nothing moves when the rich pane swaps in (#164): it was styled with the reader's 17 px / 1.7 rules while `.md-rich` is 16 px / 1.65, which shrank the title from 34 px to 32 px and pulled the second paragraph up 55 px at the swap (one line per ~11 lines on a long document). `.rich-placeholder.reader-body` now pins the base scale and mirrors the `.md-rich` rules that differ from the reader's (code-block size, list-item and task-item spacing, fixed table layout); `e2e/ssr-preview.spec.ts` holds the page's scripts back, measures every top-level block in the placeholder, releases them and asserts the same blocks in `.md-rich` are within 1 px, in light and dark, on a 3-paragraph and a 12k-word document.
- Opening a document no longer fires the shell's side requests before the editor is live (#118, task #527): the star state, the notifications poll's first tick and the share hint's collaborator and token lists now wait for the first sync (or 2.5 s), so only the collaboration token and the page's own assets reach the server before the WebSocket is open (was six requests); `markdoc:sync-acked` / `markdoc:saved` perf marks show the last 0.15–0.35 s before "saved" is the server's ack of the client's sync step 2, which is left as is because the client cannot know on its own whether its local copy carries unsynced deletions. Measured on the 12k-word document in development: warm `saved` median unchanged within noise at 2.6–3.1 s (the connect → socket-open gap is the main thread applying the local copy and mounting the panes, not the server; see the task report), so `scale.spec`'s 3.3 s budget stands; no production number was taken in this pass. Star and badge are asserted to appear within 3 s of "saved" (`dashboard-org.spec`, `notifications.spec`).
- The 12k-word document is editable sooner after opening (#118, task #510): the rich pane rebuilds its ProseMirror document once per open instead of once per Yjs transaction (text from the local copy and the server is coalesced until the first sync, or a 50 ms pause), the code pane no longer dispatches a no-op highlight update on every session change while the document loads (each one read the DOM selection and forced a layout of the freshly rendered rich pane — the 199 ms of `eq` in the #481 profile), and the collaboration token is fetched while the WebSocket opens rather than after. Live typing is unchanged (the coalescing only applies to remote text before the first sync); `scale.spec` test 1's `navigation → saved` budget drops from 6 s to 3.3 s.
- Pathological Markdown no longer freezes the browser tab (task #495, follow-up to #115): pasting or importing text with thousands of unbalanced brackets or emphasis markers in one paragraph (the 40k-`[` repro) into either pane now shows a short toast and inserts it as a fenced code block, and when such text is already in the document (written by another client or the API) the rich pane shows a *This section cannot be rendered* placeholder for that block while the code pane keeps the text editable. `parseMarkdown` runs the linear `findUnrenderable` scan first and never hands the offending paragraphs to micromark; the placeholder carries its source verbatim so the document round-trips unchanged. `e2e/pathological.spec.ts` measures both pastes and the seeded-document open (toast, code block, no long task > 1 s, typing still echoes).
- One typed word is one suggestion (task #475, issue #111): typing into the empty paragraph Enter leaves at the end of a document — in Suggesting or Editing mode — no longer re-serializes the whole document on the second keystroke, which padded every unpadded table cell (`| a | b |` → `| a   | b   |`) and, in Suggesting mode, recorded each run of spaces as a tracked insertion (*Suggestions 6* for one word). The parser started an indented paragraph's block range at its first non-blank character while the rich node kept the 1–3 leading spaces, so the binding's diff doubled the indentation, failed its round-trip check and fell back to a full rewrite; the range now starts at the indentation. The binding also drops the empty "phantom" paragraph once suggesting mode has written the text typed into it, so no blank paragraph appears above the suggestion. Unit tests assert that the Y.Text delta for ` suggested-words` is exactly that text in both modes and that the table lines are byte-identical; `review-suggestions.spec.ts` asserts *Suggestions 1*, unchanged lines 8–10 and a single insertion mark on the last line.

### Collaborating

- Agent writes can be conditional on what the agent read, so a person typing in the same document no longer loses their words (#123, task #490): `PUT /api/documents/:id/content` and `POST /api/documents/:id/suggest` accept `ifContentHash` in the body or `If-Match: "<contentHash>"` — the hash `GET /content` already returned and `markdoc_watch` reports on every `content.changed`. When the document's clean text no longer hashes to it, nothing is applied and the route answers `409 { error: "Document changed since you read it", contentHash, diff, truncated }` with the current hash and a unified diff (≤ 200 lines) of what moved since the state the caller read (`GET /content`, the events route and every API write remember it; `diff` is `null` if that state aged out of the cache). `200` responses now carry the new `contentHash`. Without the hash the write stays unconditional. The check runs inside the live-document mutation, so the compare and the write see the same state. MCP: `markdoc_read_document` prints the hash in its header line (`# Title (id …, hash …)`) and in `structuredContent`, `markdoc_replace_content` / `markdoc_suggest` take `ifContentHash` and their descriptions (and the server instructions) tell the model to pass it back; a refusal is `isError` reading *Document changed since you read it — nothing was written; re-read and retry … here is what changed:* followed by the diff. `src/app/api/documents/content.test.ts` plays agent and human: stale hash → `409` with the human's appended line in the diff and the document untouched, current hash → `200` with a new hash, quoted / weak `If-Match`, malformed hash → `400`, and the same on `/suggest`; `client-errors.test.ts` covers the MCP text; `scripts/mcp-smoke.mjs` appends, replaces with the stale hash (`isError`, "changed since", the diff) and then with the current one.
- The Comments panel lands where the work is (`9fb9cd5`, #141, issue #117, task #482): right after an agent or a collaborator created suggestions the panel opened on **Open** and said *No open comments* while the Suggestions tab sat one click away. The panel now picks its landing tab on mount — **Suggestions** when the document is in Suggesting mode or when there are pending suggestions and no open threads, **Open** otherwise — and the first suggestion that arrives while the panel is open switches to Suggestions once per mount, never again, so a user who switched back is not fought (skipped while a comment is being composed). The Open empty state links to *N suggestions waiting* when there are any. The tab strip is a real `role="tablist"` (`role="tab"`, `aria-selected`, `aria-controls`) over a `role="tabpanel"`, and `EditorShell` clears its `commentsFocus` request when the panel closes so a later reopen picks its own tab instead of replaying a stale one. `review-suggestions.spec.ts` covers landing, the once-only auto-switch and the empty-state link.
- `markdoc_watch` no longer wakes an agent on its own writes, and every event says who did it (#122, task #484): after `markdoc_append`, `markdoc_suggest`, `markdoc_comment` or a review from the same token, the next `markdoc_watch { since }` kept returning at once with a `content.changed` whose diff was the text the agent had just written (plus its own `comment.added` / `mention`), so the *suggest → presence idle → watch* loop burned a tool call and a model turn per action and a naïve agent could re-react to itself. `mutateLiveDoc` now records which token moved the clean-text hash (the `meta.agentActivity` stamp `recordAgentActivity` leaves during the write; humans typing over the WebSocket are remembered as the last typist), and the events routes attribute each hash move by walking those transitions back from the cursor's hash. Every event — `content.changed`, `comment.*`, `suggestion.*`, `review.created`, `mention`, `request.created`, `activity` — carries `actor: { id, name, login, kind: "user" | "agent", agent, self }`; events with `actor.self` are dropped by default and do not end the long-poll, `?includeSelf=1` / `includeSelf: true` delivers them, and the MCP text reads `content.changed by Copilot CLI (you)` / `(agent)` for another token. The cross-document inbox (`GET /api/agent/events`) follows the same rule for mentions the token wrote itself. `src/app/api/agent/events.test.ts`: own append → `events: []` after the full wait, another user's → `actor.self === false`, a second token of the same owner is `kind: "agent", self: false`, a person's write between two own writes is still reported; `scripts/mcp-smoke.mjs` checks *Nothing happened* after an own append and *(you)* with `includeSelf`.
- Collaboration traffic at Burke scale (#119, task #480): opening the 12k-word document delivered 266–389 KB over the WebSocket and the typist received ~3 messages per keystroke. Three causes, all fixed. The editor created its collaboration session in a `useState` initializer, which React StrictMode (development) runs twice — the discarded twin connected too, so every tab had two sockets, got the full state twice on open and every update twice afterwards (`CollabSessionOptions.autoConnect: false` + `session.connect()` in the effect; an unadopted session frees itself after 10 s). ### Accessibility

- The *Insert table* size picker is a keyboard grid and Esc dismisses the editor's floating menus (issues #160, #163, task #564). The picker was 48 plain buttons with no arrow-key handling — 18 Tabs to reach 3×3, 48 to reach Close, and a `rows × columns` label that only followed the mouse. It is now a WAI-ARIA `grid` (`row` / `gridcell` around the same `aria-label="R by C"` buttons) with a roving tabindex: exactly one cell is `tabIndex=0`, ArrowUp/Down/Left/Right move focus one cell and clamp at the edges, Home/End go to the row's first/last cell and Ctrl+Home/End to the grid's corners (`gridCell` in `src/lib/a11y.ts`, unit-tested), the label follows focus as well as hover, Enter inserts, one Tab leaves the grid for Close, and reopening starts on *1 by 1* again. In the rich pane, Esc now does — in this order — (1) collapse a non-empty selection to its head, which removes the selection bubble, (2) with the caret in a table and its floating menu showing, hide the menu until the selection moves (plugin state set by a meta transaction, cleared on any explicit selection change, announced on the editor element so the React menu re-reads it), (3) otherwise nothing, so the slash menu's Esc (its plugin runs first), *Stop following* (a window-level capture listener) and the find bar's own Esc are unchanged. The docked Comments and Version history panels deliberately do **not** close on Esc — it would fight Esc inside the comment composer — and the *Keyboard shortcuts* dialog says so. `a11y.spec.ts`: ArrowRight ×2 + ArrowDown ×2 → focus on *3 by 3* with the label `3 rows × 3 columns`, one `[tabindex="0"]`, one Tab to Close, Enter → a 3×3 table, axe 0 on the open dialog; select words + Esc → bubble count 0 and a collapsed DOM selection; click a cell + Esc → menu hidden and a typed character lands in that cell; Esc in the find bar still closes it.
- Closing a dialog puts focus back where the user was, never on `<body>` (issue #161, task #538). *Insert image*, *Insert link*, *Keyboard shortcuts*, *Connect to GitHub*, *Name this version* and *Ask an agent* are state-controlled (no Radix Trigger), and `DialogContent` remembered its return target inside `onOpenAutoFocus` — an event Radix skips when a child's `autoFocus` has already put focus inside the dialog (the four dialogs with a focused field), and one that fires after the ⋮ menu has unmounted (so for Shortcuts and GitHub the remembered element was already `<body>`). `DialogContent` now captures the opener during the render that mounts the dialog, before React commits, through `focusReturnTarget()` in `src/lib/a11y.ts`: the focused element as is (editor pane, toolbar button), or — for a menu item — the trigger that controls the menu, found via `aria-controls` / `aria-labelledby`. Esc or Cancel on the six dialogs returns to the rich pane with its selection, to the `⋮` button, or to the *Ask an agent* / *Image* toolbar button when it was activated with Enter; Apply/Insert still lands in the editor (task #437). Unit tests cover `focusReturnTarget` and `restoreFocus`; `a11y.spec.ts` walks the issue's evidence table.

With 22 rows the menu was 840 px tall on an 844 px phone, ran off the bottom and *Move to trash* could not be reached. `MenuContent` now caps every dropdown at Radix's measured `--radix-dropdown-menu-content-available-height` (8 px collision padding) and scrolls inside, so the last item is always reachable; the content element is `tabindex="0"` so the scroller satisfies axe's `scrollable-region-focusable` (Tab is swallowed by the menu anyway, so nothing else changes). `mobile.spec.ts` opens the menu on the 390 × 844 viewport in both themes, asserts ≥ 20 rows, the box inside the viewport, that it scrolls, that *Move to trash* comes into view, zero axe violations, and that the document is moved to the trash.

The *Name this version* dialog opened with focus on its Close button, so the typed name was lost and Enter dismissed the dialog: the ⋮ menu returns focus to its trigger after the name field's `autoFocus` has already run, and Radix then focuses the first tabbable element, the header's Close. `DialogContent` now hands the opening focus to `firstTabbable(content)` (`src/lib/a11y.ts`: enabled, not `tabindex="-1"`, rendered) and passes over anything inside a `[data-focus-skip]` ancestor — the dialog header carries it so Close never takes the opening focus, and the file-drop dialog's options carry it too because every option there changes the document and Enter should not fire one by accident. ### Agents

- Fix: a NUL byte (`U+0000`) in a text field no longer answers `500` with the driver's SQL statement and bound parameters (issue #185, task #586): Postgres `text` cannot hold `\0`, so `POST /api/documents`, `PUT`/`PATCH …/content`, `PATCH …/:id` (title), `POST …/comments`, `POST …/suggest`, version and token names and `POST /api/import/file` all failed at the insert and the catch-all in `src/server/http.ts` returned `err.message` verbatim — table, columns, the new id, the owner's user id and, for imports, the serialized Yjs state — to any caller with write access; the comment route had already written the thread when the activity row failed (`GET /comments` showed it), and `PATCH /content { append }` answered `200` with the text unchanged. `readJson` now walks the parsed body and refuses any string containing `\0` before the schema runs, with `400 { error: "Invalid request", issues: [{ path: ["content"], message: "Text may not contain NUL characters" }] }` naming every offending field (`nulPaths`, `NUL_MESSAGE`, `nulFree` for query strings — `?q=` uses it), so nothing is written; every remaining non-`HttpError` failure is logged and answered `500 { error: "Unexpected error" }`. `POST /api/import/file` decodes a `FF FE` / `FE FF` byte-order mark as UTF-16 (a Word "Unicode" export, PowerShell redirection) and refuses bytes that still hold `\0` after decoding — a binary renamed `.md`, UTF-16 without a BOM — as `415 "<name>" is not a text file`, converting the whole batch before creating any document so a bad third file leaves the first two unimported. The comment route's side effects (mentions, notifications, activity, request progress) run in one step after the Yjs write and, should any of them fail, the new thread or reply is removed again before the error propagates, keeping "a non-2xx status means nothing changed" true. `src/server/nul-bytes.test.ts`: each route with `"a\0b"` → `400` naming the field and the row count / content / comments unchanged; the 5-byte `nul.md` → `415`; UTF-16 LE and BE → `201` *Hello UTF-16*; a forced `Failed query … params: …` from the activity insert → body exactly `{ error: "Unexpected error" }` and `GET /comments` empty. `docs/agents.md` documents the `400`, the `500` body and the import rule.
- Webhook `documentIds` no longer accept another user's private document (#183): `POST /api/webhooks` stored any 12-char id and the dispatcher, seeing the hook *named* the document, skipped its access check and pushed that document's `comment.added` bodies and `content.changed` diffs to whoever knew the id. `createWebhook` now resolves every id with `getDocumentAccess` for the session user and answers `404 { error: "Document not found: <id>" }` like `POST /api/tokens` (#489), storing nothing when one id is bad; the dispatcher calls `getDocumentAccess` before `collectDocumentEvents` on every hook × document, `documentIds` or not, so a share revoked after the hook was created stops deliveries at the next event (the per-document cursor is dropped too: re-sharing resumes from then, the events missed meanwhile are not back-filled). `webhooks.test.ts`: a foreign id, a bogus id and a mixed list rejected at `createWebhook` and through the route, the owner and a collaborator accepted; a hook naming a shared document delivers, then nothing after `removeCollaborator`, then only new events after re-sharing. Docs: `docs/agents.md` § *Webhooks*.
- Outbound webhooks: agent events are pushed to an HTTP endpoint instead of each idle agent holding a 55 s long-poll (`cbc3f6e`, #156, issue #125, task #488). The dispatcher (`src/server/webhooks.ts`) is a server-side long-poller on the same wake sequences `markdoc_watch` waits on — `wokenDocuments` in `agent-events.ts` tells it which documents woke, then `collectDocumentEvents` runs per webhook with a per-webhook cursor, so both channels see identical events and nothing new is emitted anywhere; it starts once per process from the new `src/instrumentation.ts` (Node runtime only) and from the webhook routes as a fallback. Each delivery is `POST <url>` with the event JSON plus `documentId`, `documentTitle` and `cursor`, headers `X-Markdoc-Event`, `X-Markdoc-Delivery` (one UUID across retries), `X-Markdoc-Attempt` and `X-Markdoc-Signature: sha256=<HMAC-SHA256 of the raw body with the secret>`; the receiver has 5 s to answer `2xx`, anything else is retried after 10 s, 1 min and 10 min, and 20 consecutive failures disable the hook and send its owner a `webhook.disabled` notification (bell icon, sentence and `KIND_LABEL`); delivery rows (`webhook_delivery`, migration `0013`) are kept 7 days. Session-only REST like `/api/tokens` (a token gets `403`): `GET /api/webhooks` (with `active`, `failures`, `lastDelivery`), `POST /api/webhooks { url, events, documentIds? }` (`201`, the secret once), `DELETE /api/webhooks/:id`, `POST /api/webhooks/:id/test` (one `test` event, no retries). Settings → Agents & API access gains a **Webhooks** card: URL, event checkboxes, optional document list, the secret shown once, last delivery (`200 · 2 min ago` / `failed ×3`), **Send test** and delete. `GET /api/me` lists the user's active `webhooks` (never the secret) and `markdoc_whoami` says where events are also pushed. Tests: `src/server/webhooks.test.ts` (signing, validation, a comment delivered and signed within a second, no duplicates, unsubscribed events and other documents filtered, retries under one delivery id, disable at 20 + notification, test event, pruning), `e2e/webhooks.spec.ts` (add in Settings, secret once, Send test lands on a local receiver). Docs: `docs/agents.md` § *Webhooks* (headers, retry schedule, a Node verification snippet).
- Fix: a webhook cannot point at Markdoc itself (task #575): `POST /api/webhooks` refuses a URL whose `host:port` equals the server's own origin — the request's `Host` header (both default ports, since its scheme is unknown) and `MARKDOC_URL` when set — with `400 { error: "A webhook cannot point at Markdoc itself" }`.
